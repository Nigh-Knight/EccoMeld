    - IMPORTANT (per WARNING 1): `onStateChange` MUST be a mutable property with a no-op default, NOT a constructor parameter. This is because Hilt constructs the singleton before BridgeViewModel exists, and BridgeViewModel needs to assign the real callback post-construction in its init block:

    Three `@JavascriptInterface` methods:

    1. `createPlaylist(json: String)` — per D-03/D-04:
       - Parse JSON using `org.json.JSONObject`
       - If `found == true`: extract `path` JSONArray as `List<String>`, call `onStateChange(BridgeUiState.PathFound(path))`
       - If `found == false`: call `onStateChange(BridgeUiState.Error("No bridge path found. Try different artists."))`
       - Log via `Timber.tag("MeldBridge").d("createPlaylist: %s", json)`
       - Wrap in try/catch: on parse failure, call `onStateChange(BridgeUiState.Error("Bridge result parse error"))`

    2. `onProgress(json: String)` — per D-05/D-06:
       - Parse JSON using `org.json.JSONObject`
       - Extract `depth` (int, default 0) and `maxDepth` (int, default 0)
       - Call `onStateChange(BridgeUiState.Searching(foundHops = depth, totalHops = maxDepth))`
       - Log via `Timber.tag("MeldBridge").d("onProgress: %s", json)`
       - On parse failure: silently log and ignore (progress is best-effort per D-06)

    3. `onBridgeReady()` — readiness signal (per Research Pitfall 3, option 2):
       - Uses a mutable property `var onReady: () -> Unit = {}` (set by BridgeModule in Plan 02)
       - Dispatches to main thread, calls `onReady()`
       - Log via `Timber.tag("MeldBridge").d("onBridgeReady called")`

    Imports needed: `android.os.Handler`, `android.os.Looper`, `android.webkit.JavascriptInterface`, `org.json.JSONObject`, `org.json.JSONArray`, `timber.log.Timber`, `com.metrolist.music.ui.screens.bridge.BridgeUiState`
